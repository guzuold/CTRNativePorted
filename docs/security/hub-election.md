# Public hub election recovery

2026-10-21, Europe/Rome. Branch `hub-election`, based on `security/v0.5.5` at `f4d7cc6` after the ingress-filter commits. No push, tag or release. The ingress implementation files `hle/online_config.cpp` and `hle/net_socket.cpp` are unchanged.

## Incident and evidence boundaries

Read the supplied logs in place, without copying them. A's original public tasks 145/2, 145/3 and 145/18 occur at 18:15:09; B's corresponding tasks occur at 18:23:25 after its restart. Neither supplied log contains a `hub_*` event for that original attempt. Addresses, player names and friend codes from those logs are not included here.

The original `Host::elect_hubs` overwrote the selected hub with the current three-second DHT lookup's verified results. An empty lookup therefore discarded a previously reachable hub. Its condition-variable predicate only accepted shutdown, so notification alone could not request election. `Server::Impl::hub_task` silently fell back to local handling when no hub was available.

## Changes, values and rationale

1. **Verified candidate set:** `hub_election.hpp`, `HubElection::round/publish`; `launcher_online.cpp`, `Host::elect_hubs`. The single election worker owns candidates keyed by full code, with endpoint, successful verification timestamp, consecutive failures, activation state and source. Known endpoints are identified directly before any DHT lookup. The returned signed identity must match the saved code. An endpoint is attempted once per round even when also advertised. A live candidate survives empty DHT results and up to two direct failures; the third direct failure removes it. Independently, a verification aged **300 seconds** expires. Successful timestamps use an injected clock after the response, rather than the start of a long lookup. Selection always uses the existing `choose_hub` lowest-code rule, including self only when reachable. It never pins the previous elected hub as a selection rule.

   Memory and work are bounded to **16 retained remote candidates**. A full pool refuses additional new codes until a slot expires; it does not evict a live candidate merely because a DHT result was missing. This can limit convergence when more than 16 legitimate hubs are visible, and does not prevent malicious lowest-code generation or an eclipse. The partial-view regression covers unsaturated pools. Existing per-player hub seats remain fixed until disconnect/failure, as before; this change is not live migration of existing queues.

2. **Persistence:** `HubElection::load/save`, `runtime/user/online/hub_candidates.json`. Save candidate hints with their original last-success time using temporary-file replacement; pending saved hints also survive transient failures, but the runtime activation flag is never persisted. Read at most **64 KiB**, **16 rows**, and only timestamps less than five minutes old and not in the future. Loaded rows are inactive hints. A fresh nonce/signature response from their expected code is required before any selection. They are verified in the first immediate round; each successful verification is published before probing the next saved endpoint and before DHT search. Failed writes produce `hub_cache_error`; malformed caches are ignored. No trust/key format or friend file changes.

3. **Schedule and sampling:** `Host::elect_hubs` starts immediately, with no old three-second initial sleep. Known candidates are refreshed first, followed by one **6000 ms DHT wait** (twice the old allowance). DHT service already retains late results, so a second simultaneous lookup is unnecessary. Deduplicate announcements by IP **before** the 16-address verification limit; changing ports on one IP cannot consume the whole sample. Each identity operation retains the existing **1500 ms** network timeout. Target rounds start **60 seconds** apart with a hub, **5 seconds** apart without one, measured from round start; if work overruns, normal scheduling waits one second. An explicit task demand can wake sooner. Demands during a round coalesce. The HTTP helper's timeout is per socket operation, not a total hostile-drip deadline; the task wait itself remains bounded independently.

   `hub_gate.hpp`, `HubGate`: a separate synchronized publication/wake gate keeps network calls outside its mutex. Publication carries a steady-clock expiry, so an old hub is not returned merely because the election worker is delayed. Shutdown releases waiters and rejects late publications. Reachable self is available immediately on startup.

4. **Public task without hub:** `server.cpp`, `Server::Impl::hub_task`; `ServerConfig::await_match_hub/hub_reachable/hub_wait_budget`; `HubGate::acquire/wait_until`. Only local public tasks 145/2, /3, /15 and /18 without a seat or current hub on an unreachable PC request election and wait, for **1000 ms**. Publication wakes the task immediately. On expiry it falls back locally with a reason. Reachable self and private/non-matchmaking tasks incur no election wait. Server state locks are not held during this wait. `ServerConfig::lobby_port` defaults to unchanged port 3074 and allows isolated synthetic tests on port 29774; no launcher/retail port or protocol changes.

   **Task deadline review:** the retail v1.21 flattened ELF inspected has SHA256 `a12626f4b7547fb49e8ac810d881e2fe507d5abec38106a093165eb40e3f06cd`, compared byte-for-byte at all five inspected ranges against the pinned update eboot; see `hub-evidence/retail-task-budget.json`. At ELF VA `0x3f0310`, the base task initializer copies a global duration into object offset `0x60`; the registration code at `0x1711ed5` supplies the float constant at `0x1c385bc`, which is **10.0**. The low-level request constructor at `0x11f620` clears its timeout field; status routine `0x122c10` tests that field only when positive. The calls for player-info and token requests reach that constructor. These are retail code observations. A full ten-second server wait would consume the base budget before forwarding (which already uses a five-second HTTP timeout). One second preserves headroom. **This does not prove all runtime overrides, UI cancellation deadlines, or slow forwarding paths**; the unchanged 300-second lobby idle timeout is not evidence about task deadlines. Ten seconds is not enabled. Actual retail tolerance and both target versions remain part of the manual check.

5. **Logging:** `HubEvents::observe`, `Server::record_event`, `Host::elect_hubs`, `Server::Impl::hub_task`. Events go to the existing synchronized service JSONL log. `hub_elected`: first 16 code characters, `address`, `source` (`dht`, `saved`, `direct`, or `self`), `candidates` including eligible self. `hub_lost`: abbreviated code, address, reason (`direct_failures`, `verification_expired`, or `lower_code_or_endpoint_changed`). Transitions are logged, not every unchanged refresh. `hub_none`: service/task, `reason` (`wait_expired` or `no_candidates`), `reachable`, eligible `candidates: 0`, `wait_ms`. Existing forwarding/unreachable events and per-player seat behavior are preserved. A signed forwarding failure still logs `hub_unreachable`.

6. **False UPnP reachability:** proposal only in [hub-options.md](hub-options.md#external-reachability-confirmation-proposal-not-implemented). A callback witness needs capability negotiation; v0.5.4 cannot perform a new action. No unsupported action or successful reachability stub was added.

### Test-environment incident

The sandbox's process listing initially hid the user's running launcher. Preliminary integration probes did not validate listener startup and accidentally reached that existing service, creating synthetic lobby-task entries in its log around 18:40–18:42. They are excluded from all passing/baseline evidence. No production executable/configuration was replaced or process closed by the agent. The final fixture checks its own listener events and uses dedicated ports 29774/29780/29781–29784. The user then closed the launcher; the full existing suites were run afterward, with a process guard. Sensitive real logs remain outside the repository. The policy flood evidence keeps the final aggregate output rather than 4096 repetitive synthetic denial lines.

## Manual acceptance still required

Use two PCs unknown to each other, public matchmaking, with A already queued. Put B behind CGNAT or a poor phone hotspot. B must log `hub_elected` then `hub_task_forwarded`; A must log `hub_player_joined`. Repeat after restarting B's launcher. Then interrupt DHT access while identity HTTP still works; B must keep the hub. Stop A: after three direct failures or five-minute expiry, B must lose it and select another verified candidate if available. Check actual retail task timing, queue formation, cancellation, private invitations and mixed v0.5.4/current clients. A complete cold discovery may exceed the one-second task budget and deliberately log local fallback; the change cannot guarantee discovery on an unavailable network. No real two-PC/CGNAT race was run here.

Runtime milestones: builds and local protocol tests only; no new title/menu/track/playable-race claim. Reconstruction: zero new functions reconstructed or activated. No compatibility stubs were added or removed; this work does not certify R8 or global stub counts.
